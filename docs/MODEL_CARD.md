# Model card: Sentinel return and abuse models

> Synthetic data is used to validate the architecture, policy behaviour, auditability, and coordinated-pattern detection. Real deployment would require merchant-specific historical data and prospective validation.

## 1. Intended use

- **What they do:** estimate two separate probabilities for an e-commerce order at checkout, after the payment method is chosen and before the order is confirmed:
  - `p_return`: the order will be returned or exchanged within 30 days of delivery
  - `p_abuse`: the order will be confirmed as return or refund abuse (wardrobing, empty box or swapped item, a false item-not-received claim, coordinated rings)
- **Who uses the output:** a deterministic policy engine that prices four actions, and a human reviewer who sees both scores and the evidence behind them.
- **The models never choose an action.** `p_return` is structurally excluded from action selection (guardrail G1). `p_abuse` enters an expected-cost calculation, and six guardrails constrain the result.
- **Out of scope:**
  - credit decisions
  - identity verification
  - any customer-facing score
  - use on real customers without retraining and prospective validation on the merchant's own data

## 2. Training data

- **The world:** a seeded synthetic world (seed 20260901) of about 2,940 accounts and 10,150 orders over 365 days. The return rate is 23.0 %, and 3.5 % of orders are confirmed abuse.
- **Inflated prevalence:** abuse prevalence is **deliberately higher than realistic** so that the test split has enough positives (97) to measure anything.
- **Hard negatives are included on purpose:**
  - households
  - offices, hostels and PGs
  - refurbished-device owners
  - high-value genuine carts
  - "unconfirmed abusers" who are labelled 0 (realistic label noise)
- **Rings:** R1 to R4. Ring R3 exists **only** in the test period, so it measures cold-start detection.
- **Chronological splits:**

  | Split | Days |
  |---|---|
  | TRAIN | D1–D200 |
  | CALIBRATION | D231–D275 |
  | TEST | D306–D365 |

  The gaps between them are at least as long as the return window.
- **Point-in-time features:** every feature uses only events strictly before the order's timestamp. Confirmations count from the time they were confirmed, not from the date of the original order. A 14-control leakage test suite enforces this.
- **Unresolved disputes** (79 of 495) are excluded from training and evaluation. A sensitivity check re-scores with all of them treated as 0 and then as 1.

## 3. Model details

| | Return model | Abuse model |
|---|---|---|
| Features | 11 order and account features, including matured return history | 17 features: relationship graph (device, token, address links, component, proximity to confirmed abuse, bursts), account age, prior orders, flagged claims in the last 180 days, order value, category |
| Deliberately excluded | — | historical return rate, payment method (a proxy for income), CLV (a proxy for wealth), IP address, name, pincode |
| Constraints | monotonic +1 on return history and size bracketing | monotonic +1 on every evidence feature: more evidence can never lower risk |
| Calibration | isotonic, fitted on the CALIBRATION slice | sigmoid (one-feature logistic regression), fitted on the CALIBRATION slice |

**Explanations** use ablation attributions, measured in probability points and never summed, plus reason codes rendered from fixed templates. No SHAP is used and no text is generated by an LLM.

## 4. Performance (TEST split, synthetic)

**Abuse model**

| Metric | Value |
|---|---|
| PR-AUC with graph features | **0.814** |
| PR-AUC, same model without graph features | 0.527 |
| Recall on cold-start ring R3 (never seen in training), with the graph vs without | **0.727** vs 0.143 |
| Genuine block rate, hard-negative archetypes (households, offices, refurbished phones) | **0.0** |
| Precision of BLOCK decisions under policy v1.0 | 0.875 |

**Return model:** TEST PR-AUC ≈ 0.39. That is above the gate of 1.5 × prevalence but modest. A score built on the *true* archetype reaches only 0.391, so the ceiling is in the data. The return model is operational context only and drives no action.

**Separation:** across frequent returners, the correlation between `p_return` and `p_abuse` is below 0.2, so the models do not treat frequent returners as abusers.

## 5. Fairness: the new-account disparity

**Sentinel places far more friction on new accounts than on anyone else. This is a measured property of the system, not a small-sample artefact.**

| Cohort (TEST, under policy v1.0) | Customer friction rate | Genuine block rate |
|---|---|---|
| Accounts under 30 days old | **36.1 %** | **0.74 %** |
| Accounts 30–365 days old | 4.8–5.9 % | 0.00 % |
| Accounts over 365 days old | 4.8–5.9 % | 0.09 % |
| Cash on delivery | 7.3 % | — |
| Prepaid | 8.5 % | — |

- **Why it happens:** `account_age_days` is the abuse model's most-used feature (843 splits). Abusers in the data, like abusers in reality, often use fresh accounts.
- **Why the feature is kept:** it is genuinely predictive. Removing it would push the same signal onto `prior_orders`, which carries the same information under a less honest name. The disparity is **disclosed, not engineered away**.
- **What limits the harm:**
  - Newness alone can never cause a block. BLOCK needs at least two corroborating signals, one of them a device, a payment token or prior flagged claims (G2), plus a confidence floor (G3).
  - New customers are valued at a lifetime-value floor, so a block always carries a real cost.
  - Most of the friction is **prepaid-only or manual review**, not refusal.
- **Payment method is neutral:** COD at 7.3 % friction against prepaid at 8.5 %, because payment method is excluded from the abuse model.
- **Before real deployment:** monitor friction by account-age cohort, and consider a friction budget or a softer first-order path for new accounts.

## 6. Known limitations

1. **Synthetic data.** The figures validate the architecture and the policy's behaviour, not real-world effectiveness.
2. **Selective labels.** In production, blocked orders produce no outcome, and Sentinel's own flags steer investigations. A randomised holdout would be needed; it is out of scope.
3. **Investigation-coverage bias.** Confirmed abuse clusters where investigators look.
4. **Redundant graph evidence.** The confirmed-neighbour features are individually predictive but get zero splits in the full model, because correlated features identify the same rows first. Reason codes are therefore **evidence statements**: they fire when the fact is true and say when their own contribution is small.
5. **Cost assumptions.** Every monetary value is a demonstration assumption (policy v1.0). The tuned fixed-threshold baseline has a lower realized cost (₹1,60,112 vs ₹1,95,313 per 1,000 orders). The difference is the guardrails' price for avoiding wrongful blocks: about ₹9,211 per block avoided, 2.05× the policy's own modelled false-block cost.
6. **Review capacity** is not modelled. The policy sends about 65 orders per 1,000 to review.

## 7. Privacy

- Identifiers arrive as 32-hex HMAC digests, and the API rejects anything else.
- No names, addresses, IP addresses or pincodes are used as features.
- The graph shows masked labels only.
- Cross-account linkage is personal-data processing. A real deployment needs purpose limitation, notice and retention rules under applicable law (for example, India's DPDP Act, 2023). This is not legal advice.
